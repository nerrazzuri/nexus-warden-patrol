# 日志设计

用户 11-10：日志分两类，一类给用户自己看，一类给工程师维护时用。问题定位的时候，日志往往是唯一能看的东西，所以必须写得详细。起因是 liang-d5 审出的 L1–L5（操作日志太简略、站点日志几乎全是轮询记录、机器人日志对不上任务、App 没有日志、日程没跑时显示的原因不对）。

## 用户定下来的

- 两类日志分开：
  - **用户看的**：网页的活动日志、App。写成中文的一句话，保留 **1 年**。
  - **工程师看的**：诊断包、日志文件。格式统一，保留 **30 天**，并限制总大小。
- 日程没跑、机器人离线这类**系统事件也给用户看**。
- **机器人的日志也存到站点上**，按 30 天保留。
- 日志第一期先做，排在「两种开法」「卡住脱困」之前。

## 编号把各条记录串起来

每条记录都带上能用的编号：

| 编号 | 是什么 |
|---|---|
| `req` | 站点每个请求一个 |
| `task` | 任务号 |
| `pt` | 第几个点，从 0 开始 |
| `robot` | 机器人编号 |
| `cmd` | 命令号 |

站点把任务派给机器人时，任务号跟着下去；机器人、导航转接写的日志也带上它。拿一个任务号，就能把站点、机器人两边的记录对上。

## 一、用户看的

1. **操作记录**（`audit` 表，网页的活动日志）。每一条都要有：
   - 对象：哪台机器人、哪个防区、哪条路线、哪个点；
   - 前后变化：改之前、改之后；
   - 来源：网页、App、日程或系统；
   - 结果，被拒时写出原因。

   兜底规则：
   - 路径里能看出对象的，自动填上；
   - 请求内容去掉敏感字段后存一份。敏感字段是名字里带 `password`、`pin`、`token`、`secret`、`key`、`otp`、`code` 的。

   另有覆盖测试：所有写接口都要留下对象或详情，不然测试失败。
2. **系统事件**（`site_events` 表，在活动日志里和人的操作排在同一条时间线上）：
   - 日程到点跑了，或者没跑，带真正的原因；
   - 自动派遣；
   - 机器人上线、离线；
   - 告警产生、升级、解除；
   - 巡逻每个点的结果。

   日程「没赶上就跳过」（missed）的那一条，要带上之前被挡下的原因（L5）。

## 二、工程师看的

3. **站点运行日志**：
   - 成功的 GET 请求放进 `logs/access.log`；主日志只记事件。
   - 失败的请求要写原因、是谁、客户端地址。TLS 握手失败时写出客户端地址。
   - 每行格式：时间（带时区）、级别、模块、编号、事件、`键=值`。
   - 级别能调：启动参数 `--log-level`；工程师在网页上可以开「详细日志 N 分钟」，到点自动恢复。
   - 按天切分文件，保留 30 天，限总大小。
4. **机器人日志**：
   - 导航的每一行都带 `task`、`pt`、点名、地图版本；每一段写结果、原因码、耗时。
   - 状态变化要记：定位、守卫、急停、回充、退回备用规划。
5. **机器人日志收到站点**：
   - 代理把各服务的日志按批传到站点，走现有的加密连接。断网时先存在本机，恢复后补传。
   - 站点按机器人分开存，保留 30 天，限总大小，快满时删掉最旧的。
   - 诊断包能按时间段、机器人、任务号导出。
6. **App**：
   - 在本机留最近几天的日志文件，release 版也写。
   - 加一个「导出诊断信息」按钮，打出来的包含本机日志、设备型号、版本。

## 验收

拿真实的问题回放，只看日志就要能定位到原因：

- 日程没跑（A 只许手动派）；
- 临时路线跳点；
- 叫停；
- TLS 握手失败；
- Nav2 没就绪，退回备用规划。
