# W43 一期：站点健康、发版升级、日志故障 方案

> 2026-11-26 用户：一期也做站点健康（D）、发版升级（B）、日志故障（E），后台租 VPS，公司只看不违反 PDPA 的。
> 全貌见 `docs/W43-公司后台-全貌.md`，证书那两块（A、I）见 `docs/公司后台-一期-方案.md`。
> 这份写 D、B、E 三块怎么做。**用户批准之前不开工。**

## 一、先说现在已经有的（都核过代码）

这三块不是从零做。站点上能用的东西大多已经在了，缺的是「送到公司」那一段：

| 已有 | 在哪 | 这次怎么用 |
|---|---|---|
| 体检：库、盘、备份、推送、机器人在线、证书到期、后台道卡没卡、版本，每项好 / 不好 + 一句话 | `health.py` `HealthDesk.checks` | D 的心跳直接拿它 |
| 运行指标：每 5 分钟一笔，留 30 天 | `health.py` `HealthDesk.record` | D 的趋势 |
| 诊断包：不带密钥、令牌、库、照片录像、位置，配置和日志打码 | `health.py` `support_bundle` | E 的故障包 |
| 问题单：App 上谁都能传日志，给一个编号 `NW-MMDD-XXXX` | `problem_reports.py` | E 的故障单入口 |
| 机器人日志：机器人传给站点，留 90 天 | `robot_logs.py` | 进故障包 |
| 被拒记录：没有出厂证书、芯片对不上的机器人想加入 | 站点库 `company_reports`，`company-reports` 命令导出 | E 自动上传 |
| 升级：网页传签名包 → 站点、机器人、App 都能升，起不来自动退回 | `releases.py`、`release_queue.py`、W55 | B 只补「从后台下载」这一步 |
| 网页「软件升级」页上的「在线下载」按钮 | 网页，一直灰着，等站点联网 | B 把它点亮 |

## 二、站点怎么跟后台说话

```
客户站点 ──HTTPS 往外连──▶ 公司后台（VPS，吉隆坡优先）
   ▲                              │
   └── 机器人、手机照旧只连站点 ──┘ 后台从不主动连站点
```

- **只往外连**：站点去找后台，后台从不连进客户网络。客户防火墙不用开端口。
- **机器人不连后台**：机器人的状态、日志都经站点。4G 上的机器人也一样。
- **站点怎么证明自己是谁**：
  - 后台给每个客户站点开一个**登记码**（一次有效、7 天）。
  - 装机或者以后在站点网页「设置 → 厂家后台」填登记码，站点生成自己的一对钥匙，后台记下公钥、发一张站点证书。
  - 以后每次连都用这张证书（双向 TLS）。站点主机换了要重新登记，旧的在后台作废。
- **后台怎么证明自己是谁**：正规 HTTPS 证书（域名）。升级包另外有签名、站点自己核（见第四节）。
- **开关**：站点网页「设置 → 厂家后台」：
  - 总开关，加三个分开关：发健康状态、查新版本、发错误摘要。
  - **默认开**（发的都是认不出人的设备数据，合同里写明）；客户能关。
  - 关了以后：升级退回手工传包，健康、日志就不发。站点本身什么功能都不少。
- **断网**：后台连不上，站点照常工作，不报警、不影响值守；攒着的心跳只留最近一条，连上了补发。

## 三、D 站点健康

### 站点发什么

每 **5 分钟**一次心跳。只有第一档的设备数据，**不带**画面、地图、位置、告警内容、账号、手机号。

| 项 | 例子 |
|---|---|
| 站点 | 站点编号、软件版本和构建号、开机时长、盘剩多少、备份上次成功时间、站点证书到期 |
| 体检 | 每一项好 / 不好，加那一句话（体检原文里有名字、IP 的先打码） |
| 每台机器人 | 序列号、型号、在线 / 离线、最后在线时间、电量、充没充电、软件版本、故障码、急停有没有按着、证书到期、盘剩多少 |
| 告警 | 现在开着的 P1、P2、P3 **各几条**，今天各几条 |
| VPN、对时 | 隧道起没起来、钟差多少 |

### 后台显示什么

- **站点列表**：每个站点一行，红黄绿。客户名、在线 / 离线（多久没心跳）、机器人几台在线、版本、最要紧的一条问题。
- **站点详情**：体检每一项、每台机器人一行、30 天趋势（盘、在线台数、开着的告警数）。
- **机队**：所有机器人一张表，按版本、按型号、按故障码筛。

### 后台什么时候叫人

发给值班工程师（后台网页上有，另外发邮件；以后再加 App 推送）：

| 情况 | 级别 |
|---|---|
| 站点 30 分钟没心跳（站点没把开关关掉的） | 要处理 |
| 机器人离线超过 2 小时，或者报了故障码 | 要处理 |
| 证书 30 天内到期、盘剩不到 10%、备份 24 小时没成功 | 提醒 |
| 站点版本比最新的旧两版以上 | 提醒 |

**不叫人的**：客户站点上的入侵、看见人这些告警。那是客户和保安的事，公司看不到内容，也不该插手。

## 四、B 发版升级

### 现在

台式机签好发行包（站点包、机器人包、App 安装包），传到私有 GitHub 仓库，再由人下载、传到每个站点的网页上。

### 以后

> 2026-11-26 用户：**发版的签名直接在后台做，台式机现在只是临时的**。

```
GitHub 发行闸（编译、全部测试，现在就有）──▶ 后台取没签名的包 + 闸的记录
                                                  │
                    后台核：闸过了、提交对得上 → 管理员点「发布」→ 后台用发行中间钥匙签名
                                                  │
                                站点每 6 小时问一次「有新版吗」→ 下载、自己核签名
                                                  │
                              网页、App 提示管理员「有新版本」，管理员点了才装
```

- **编译不在后台**：编译、打包、跑测试照旧在 GitHub 的发行闸里（`release.yml`）。VPS 小，不装安卓工具链、
  不编机器人的包。闸跑完，后台把没签名的包和闸的记录取过来，核一遍（是闸过了的那个提交、包的指纹对得上），
  这一步就是现在 `make_release.py --gate` 做的事，挪到后台。
- **签名在后台，用中间钥匙**，跟 A 块证书一个办法：
  - 发行**根钥匙**离线（加密 U 盘），一年签一次后台的**发行中间钥匙**，出事时签作废名单。
  - 后台用中间钥匙签每一个发行包。私钥加密放着，后台启动时人输口令才解开。
  - 站点、机器人核两步：先用根公钥核中间钥匙证书（用途是发行、没过期、没作废），再用中间钥匙核这个包。
    **要先发一版认这种签名的站点和机器人**；现在的包（根钥匙直接签）照样认。
- **风险要说清楚**：钥匙在线上，后台被攻破的话，攻破的人能签出站点、机器人都认的假包。所以：
  - 发布要**管理员 + 手机验证码**。**第二个人批准**（一个人点发布，另一个人确认）用户 11-26 定：后期、客户上量了再做。
  - 只签**闸过了的提交**：后台不收别处来的包，闸的记录要跟 GitHub 上那次运行对得上。
  - 每次签名都进操作记录，后台通知所有管理员「刚签了第 N 版」，不是自己点的马上看得出来。
  - 出事：根钥匙签作废名单 → 那把中间钥匙作废，作废以后签的包站点、机器人都不认 → 签一把新的。
- **安卓 App 的签名钥匙**（证书 `a039e0f5…`）也挪到后台。这把**没法用中间钥匙**：安卓规定同一个 App 永远要同一把钥匙，
  丢了就再也发不了升级。所以后台上加密放、启动时输口令，**另外离线备份两份**（加密 U 盘 + 保险柜）。
- **后台存、后台转**：签好的包放在后台，站点来下载。站点下载以后跟现在手工上传一样**自己核签名、核指纹**，核不过就扔掉。
- **不自动装**：下载好只提示，**管理员点了才装**，装法跟现在一模一样（站点升级、机器人等充完电空闲时换、App 登录提示）。
  以后要「夜里自动装」再加开关。
- **分批放**：后台上每个版本有一个「给谁」：
  - 先给**试点**站点（自己的演示站点、愿意先试的客户），过几天再给所有站点。
  - 也能只给某几个站点（比如修某个客户的问题）。
- **停发**：发现某一版有问题，后台点「停发」：
  - 还没下载的站点不再拿到。
  - 已经下载、没装的，站点上标「厂家已停发，不建议安装」。
  - 已经装了的，网页提示「建议退回上一版」（退回现在就能做）。
- **哪个站点在哪一版**：心跳里有，后台「机队」页能按版本筛。
- **App 安装包**也走这条路：站点下载下来，手机登录时照现在的办法提示升级。
- **下载量**：机器人包和 App 各几十 MB，一个月几次，VPS 流量够。站点按 6 小时问、错开时间，不会一起来下。

## 五、E 日志故障

三条路：

### 1. 错误摘要（自动，默认开）

- 每天一次，站点把**站点、机器人、App、网页**过去 24 小时的**报错**汇总发上来：哪个服务、什么错、几次、第一次和最后一次时间。
- **只发报错那一行**，不发前后文。上传前在站点上去掉：用户名、IP、地图坐标、人员检测框、文件路径里的名字、长串十六进制、令牌，换成编号。
- 后台按「哪一版、哪个服务、什么错」合并，看得出「36 版的定位在三个站点都报同一个错」。

### 2. 故障包（业主点了才发）

- 站点网页「诊断 → 打包日志」、App 的问题单，现在都是下载到本地。加一个按钮「**发给厂家**」：
  - 点之前写清楚：会发哪些（日志、体检、机器人诊断，**默认不带照片和地图**）、在厂家后台留 90 天、谁能看（公司工程师）。
  - 要带照片或地图，得再勾一次。
  - 确认了才传，传完给一个编号，跟问题单编号一样。
- 后台收到就开一张**故障单**。

### 3. 被拒记录（自动）

- 站点库 `company_reports`（没有出厂证书、芯片对不上的机器人想加入）：现在要人跑命令导出、手工传。改成随心跳自动发。
- 这里只有序列号、芯片编号、原因，认不出人。后台跟 A 块的设备登记表对一下，能看出仿冒、换主板。

### 故障单

- 后台一张单：哪个站点、哪台机器人、什么问题、附了哪些故障包、谁在处理、处理到哪一步、结论。
- 换件、返修记到 A 块的设备登记表里那台机器人名下（哪天换了什么）。
- 故障包 90 天后自动删，故障单本身留 3 年。

## 六、站点、机器人、App 要改什么

| 站点 | 新的「厂家后台」模块：登记、心跳、查新版本 + 下载、错误摘要、发故障包、发被拒记录；设置页开关；「在线下载」点亮；停发提示 |
| 站点日志 | 错误摘要的打码规则，跟诊断包那套合起来，**站点上先打码再发** |
| 机器人 | 不用改（都经站点） |
| App | 问题单加「发给厂家」；升级提示里显示「厂家已停发」 |
| 网页 | 设置页「厂家后台」；诊断页「发给厂家」；升级页在线下载和停发提示 |
| 后台 | 站点登记、心跳收和存、站点列表 / 详情 / 机队、叫人、发行包仓库和分批、错误摘要合并、故障包和故障单 |
| 发行闸 | `release.yml` 跑完把没签名的包和闸的记录留给后台取；`make_release.py` 的核对、签名挪进后台（台式机这一步以后不用） |

## 八、用户定的（2026-11-26，「四条按建议来」）

1. ☑ **默认开**（只发设备数据，合同里写）。客户能关。
2. ☑ **叫人**：先发邮件 + 后台网页。WhatsApp、App 推送以后再说。

## 附：客户许可和到期是做什么的（用户 11-26 问）

这是三期 G 块里的一项，**还没定要不要做**。说的是：后台能不能管「这个客户能用多久、能用哪些功能」。

- **许可**：每个客户站点有一张后台签的「许可」，写着这个站点能管几台机器人、开了哪些功能（比如以后的人脸库、车牌、集中监控）。
- **到期**：许可写到哪天。到期以后怎么样，有几种做法：
  - **只停服务**：不能在线升级、不能发故障包给厂家，**巡逻、报警、值守照常**。
  - **停新功能**：付费功能关掉，基本巡逻照常。
  - **整个停**：不建议。安防设备到期就停，出了事责任在我们。
- **什么时候需要**：
  - 机器人**买断**、软件不另收钱：不用做许可。
  - **按年收服务费**（升级、远程支持、后台监控）：要做，至少做「只停服务」那一种。
  - **功能分档卖**（基础版、高级版）：要做功能开关。
- **我的建议**：先不做。等定了怎么卖（买断还是按年），再决定做哪一种；真做的话只做「只停服务」，不碰巡逻和报警。
