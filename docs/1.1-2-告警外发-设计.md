# 1.1-2 告警推到 WhatsApp / Telegram / 邮件（设计）

11-28 定。用户：「继续把所有1.1功能都做了」。解决的问题：保安主管都在 WhatsApp 上，不能要求每个人都装我们的 App。

## 定下来的

| 项 | 定的 | 为什么 |
|---|---|---|
| 渠道 | WhatsApp（Meta Cloud API）、Telegram（机器人）、邮件（SMTP）、webhook（JSON，可签名） | 马来西亚主管用 WhatsApp；Telegram、邮件不花钱；webhook 给集成商、监控中心 |
| 谁配 | 管理员在网页「系统」页「告警渠道」里加、改、发测试、删 | 跟推送测试放在一起；保安不用管 |
| 发哪几级 | 每个渠道自己勾，默认只 P1，可以加 P2 | P2 多，默认不打扰主管 |
| 发什么 | **只发文字**：站点、级别、告警标题（按种类翻译）、机器人、站点时间，再加一句「打开 App 或网页处理」 | 跟决策 53 的推送一样：照片、位置出站点到第三方（Meta、Telegram）有 PDPA 问题。要发照片以后单独做成选项、默认关 |
| 语言 | 每个渠道选 English / 中文，默认 English | UI 默认英文 |
| 升档 | 升到下一档还没人确认，再发一次，写「仍未确认」 | 跟推送一样 |
| 不发的 | 已经有人确认、解决了的；一个小时还没发出去的；渠道停用、删了的 | 过时了再发没意义 |
| 上限 | 每个渠道每小时最多 30 条，超了的不发、记原因 | 告警风暴不刷爆主管手机；WhatsApp 按条收钱 |
| 发不出去 | 退避重试（10 s 起，最多 5 分钟）；连续 10 分钟发不出去报 P2「告警外发发送失败」（`notify_failed`，0x010D），发出去一条自动解决；这条 P2 自己不外发 | 渠道坏了要有人知道，不能自己报自己 |
| 密钥 | 机器人令牌、WhatsApp 令牌、SMTP 口令、webhook 签名密钥用站点 `secrets.key` 整串加密存；网页只进不出（改的时候空着 = 不变）；审计里不记 | 跟摄像头口令一样 |
| 一定会发 | 告警写库的同一个事务里排进 `notify_outbox`，站点重启也在 | 跟推送一样 |

## WhatsApp 要客户自己做的

WhatsApp 只许企业用 **Meta 批过的模板** 主动发消息。客户（或我们代办）要：

1. 在 Meta Business Manager 开 WhatsApp Business 账号，拿到 **Phone number ID** 和 **永久访问令牌**。
2. 建一个 Utility 类模板，比如名字 `nexwar_alert`，正文三个变量：
   `Nexus Warden alert: {{1}}. Robot: {{2}}. Time: {{3}}. Open the Nexus Warden app to handle it.`
3. 模板批下来以后，在「告警渠道」里填 Phone number ID、模板名、模板语言、令牌、收件人手机号（带国家码）。

费用按 Meta 的会话价算（马来西亚 Utility 一条几分钱），由客户的 Meta 账号付。

## webhook 的报文

`POST` JSON：`site`、`alert_key`、`level`、`kind`、`title`、`robot`、`time_ms`、`tier`、`text`。填了签名密钥就带
`X-Nexwar-Signature: hex(HMAC-SHA256(密钥, 原始请求体))`。

## 没做、以后做

- 发照片（默认关的选项；Telegram、邮件好做，WhatsApp 要带图的模板）。
- 在 WhatsApp / Telegram 里直接回「确认」。
- 处理结果再发一条（「已由 Gina 确认」）。

## 外审 1.1 第 1 轮改的

- 一个渠道几个收件人，前面的发到了、后面的没发到：记下发到了谁，重试只发没发到的（以前整条重发，发到的人一遍遍收）。每小时上限按「发出去过」的条数算，发到一半的也算一条。
- 对方回的错误正文可能带着请求地址（Telegram 的令牌就在路径里）、口令：进日志、库、渠道列表、「发一条测试」的回包之前抹掉。

## 外审 1.1 第 2 轮改的

- 一个渠道的收件人每个都试一遍：前面的坏了不挡后面的。
- 邮件服务器拒了一部分收件人：记下收了的，只重发被拒的（以前当成全发到了）。
- 「告警外发发不出去」这条 P2 只在真发成了一次以后才自动关（以前积压的消息过期作废了也算恢复）。
- 发送时出了别的异常（比如令牌里粘了换行，地址不合法），只记异常的类型，不带原文（原文里有令牌）；保存的时候就拒掉带换行、控制字符的密钥。

## 外审 1.1 第 4 轮改的

- 各渠道各发各的：几个渠道一起发，每个渠道一拍最多发 20 秒，剩下的下一拍接着。坏掉的渠道一直超时只拖它自己，不挡别的渠道、不让别的渠道的告警排到过期。

## 外审 1.1 第 5 轮改的

- 每个渠道各取各的队列（每渠道一拍最多 100 条）：坏渠道积压再多，也占不掉别的渠道的名额。所有渠道同时发（最多 20 个，跟渠道上限一样）。
- 20 秒预算一路传到每个收件人、每次网络调用（一次最多等剩下的时间，至少 1 秒）：一条消息十个收件人都超时，也拖不过预算。时间到了，发到的记下，没轮到的下一拍接着，不算失败、不退避。

## 外审 1.1 第 6 轮改的

- 收件人轮转：每条记下这一轮试过、没发到的收件人，下一次先发还没试过的。前面几个一直超时，后面的也轮得到；剩下的都试过一遍再从头来。
- 邮件：SMTP 每一步（STARTTLS、登录、每个收件人、发正文）收发之前都按剩下的时间重设超时，到点就断，慢服务器也拖不过这一拍的预算。

## 外审 1.1 第 7 轮改的

- 加看门狗：到了这一拍的截止时间，直接掐断正在用的连接（邮件、Telegram、WhatsApp、webhook 都一样）。对方一次回复里一行一行慢慢回、零零碎碎地传，也拖不过预算；掐断后读到的半截不算发成。邮件发完正文、在最后道别（QUIT）时到点的，照样算发成了（不重发）。
